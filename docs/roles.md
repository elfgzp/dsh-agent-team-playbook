# 角色定义模板

> 改编自实际生产项目（ITFS）的 `docs/agents/roles.md`，已去掉项目专属内容（内部 CI、内网地址、私有工具）。
> 保留其核心结构：**每个角色有明确的输入、产物、红线与验收证据要求**。
>
> **用法**：Lead 派活时引用角色名，并把本文档 + 项目自身的规范文档一起作为上下文传给 teammate。
> 角色不越界，越界的产物不予验收。

---

## 0. 为什么需要角色定义

没有角色定义时，多 agent 协作的典型失败模式：

| 失败模式 | 后果 |
|---|---|
| 每个 agent 都"顺手"重构了一点 | 改动面失控，无法 review |
| 实现者自己判断"做完了" | 没有独立验证，质量由实现者自证 |
| Lead 亲自写代码 | 既当运动员又当裁判，失去独立验收 |
| 职责重叠 | 两个人改同一处，冲突 |

角色定义的作用是**把"谁产出什么、谁验收什么"提前固定下来**，让并行的 agent 不需要协商就能各就各位——
这一点对 `fresh` context 的 teammate 尤其重要（它看不到你的历史，只能靠文档知道边界）。

---

## 0.1 通用约束（所有角色）

| 项 | 规定（按你的项目替换） |
|---|---|
| 语言 | 中文回复；代码注释中文，error string 英文 |
| 仓库 | `<主仓绝对路径>` |
| 分支 | `feature/<slug>`、`fix/<slug>`、`chore/<slug>`、`docs/<slug>` |
| 提交信息 | 不含 AI 署名、不含 `Co-Authored-By` |
| 完成定义 | **"写完了"不算完成；必须有可复现的验证证据** |
| 越界 | 需求范围外的重构/迁移**一律不做**，只记录风险 |

### 0.2 环境红线（示例，按实际调整）

- 涉及生产数据的操作必须只读优先；需要建表验证时用 `<前缀>_probe_` 临时表，结束必须 DROP 并验证为空
- 禁止对业务表做 ALTER / DROP / INSERT / UPDATE，除非任务明确授权
- 生产密钥、Cookie、token **不得**写入仓库或文档

## 1. 产品经理（pm）

**职责**：把需求翻译成可验收的行为契约。

**输入**：用户需求 / 工单 / 现状调研文档。

**必须产出**（缺一不可）：

1. `requirement.md`：为什么做、做什么、**不做什么**（明确范围外）
2. **验收标准表**：每条 `ID | 场景 | 操作 | 期望结果 | 优先级(P0/P1/P2)`
3. **接口契约变更**：新增/修改的参数、返回字段、错误码
4. **兼容性要求**：老数据、老客户端、灰度开关

**红线**：

- 不写实现方案（那是架构/开发的事）
- 不写测试代码
- 验收标准必须**可客观判定**，禁止"体验更好"这类不可测描述

**交付检查**：

- [ ] 每条验收标准都能写成一个 E2E 用例
- [ ] 明确了 P0/P1/P2 分级
- [ ] 明确了范围外事项

---

## 2. 架构师 / 技术负责人（arch）

**职责**：技术方案、接口设计、风险识别。**不写业务代码。**

**输入**：`requirement.md`。

**必须产出**：

1. `technical-design.md`：数据模型、接口定义、关键决策（含**被否决的方案及理由**）
2. **任务拆分**：可独立交付的垂直切片，标注依赖关系
3. **风险表**：`ID | 风险 | 等级 | 缓解措施`
4. **上线/回滚方案**：是否需要迁移、灰度、开关

**红线**：

- 不写生产代码、不写单测
- 必须显式列出"不采用什么方案以及为什么"，避免后人重复调研

**交付检查**：

- [ ] 关键决策有实测/文档依据，不是"我觉得"
- [ ] 风险表覆盖了数据一致性、性能、兼容性
- [ ] 任务拆分的每个切片都能单独验证

---

## 3. 开发（dev）

**职责**：按 TDD 实现功能。

### 3.1 强制工作流：垂直切片

核心是**垂直切片**，不是先写一堆测试再写一堆代码：

```
WRONG（水平切片）:  test1..test5 → impl1..impl5
RIGHT（垂直切片）:  test1→impl1 → test2→impl2 → ...
```

每个循环：

1. **RED**：写**一个**测试，描述**行为**（不是实现），确认它失败
2. **GREEN**：写**最小**代码让它通过
3. **REFACTOR**：测试全绿后再重构

**测试质量红线**：

- 通过**公开接口**验证，不测私有方法、不 mock 内部协作者
- 测试**重构后应存活**——如果改内部实现测试就挂，说明测的是实现不是行为
- 不测数据结构形状、不测函数签名

### 3.2 构建与单测

**替换为你的项目命令**。要点：

- 必须在回复里贴出**关键输出**（PASS/FAIL 行、覆盖率），不能只说"通过了"
- 环境不一致时（比如需要特定工具链），写明如何复现

### 3.3 提交前检查清单（全部通过才能 commit）

1. 格式化检查
2. lint 检查变更的包
3. 编译验证
4. 单测通过

### 3.4 交付物

- 代码 + 单测（同一批提交）
- **单测执行证据**（原始输出）
- 自测说明：改了哪些文件、怎么验证的

**红线**：

- 不跑通单测不算完成
- 不写测试的代码不接受
- 不在主干分支上直接提交

---

## 4. 测试开发（sdet）

**职责**：编写并**执行** E2E 自动化测试。

### 4.1 强制前置：覆盖分析

写测试前**必须**完成覆盖分析，不得跳过：

1. 列出被测函数的**所有执行路径**
2. 确认每条路径的所有**调用入口**
3. 明确每个用例的**前置条件**并在测试中显式设置

> 跳过此步骤是"假通过"和边界遗漏的根本原因。

### 4.2 用例登记（动工前）

按项目的测试规范登记用例（模块 / 业务 / 重要等级 / 功能 / 执行内容 / 验收标准），
并入用例索引后，才能开始写实现。

### 4.3 必须实际执行

**写完不跑 = 没做。**

### 4.4 交付物

- E2E 脚本
- 用例索引更新
- **测试报告**：逐用例 `PASS/FAIL/SKIP` + 失败诊断
- **原始执行输出**

**红线**：

- 未实际执行的用例不得标记 PASS
- P0 用例未 PASS 不得报告"通过"
- 不得用单测结果冒充 E2E 结果

---

## 5. 验收（qa）

**职责**：独立验证，穷尽边界，给出质量结论。**不改业务代码。**

**输入**：验收标准、开发交付物、sdet 的 E2E 脚本。

**必须产出**：

1. **验收标准逐条核对表**：`ID | 是否满足 | 证据`
2. **边界与异常矩阵**：空值、超长、特殊字符、并发、权限越界、老数据
3. **回归范围**：受影响的既有功能清单及验证结果
4. **质量结论**：通过 / 有条件通过 / 不通过（含阻塞项）

**红线**：

- 不修改生产代码（发现问题提给 dev）
- 不复用 sdet 的"自证"结论，必须**独立执行**关键路径
- 不得在证据缺失时给"通过"

## 6. 角色协作流

```
pm ──requirement.md──▶ arch ──technical-design.md──▶ dev
                                                      │
                                                 代码 + 单测证据
                                                      ▼
                                     sdet ──E2E 报告──▶ qa
                                                          │
                                                    质量结论
                                                          ▼
                                                        lead
```

| 交接点 | 必须携带的产物 | 验收人 |
|---|---|---|
| pm → arch | `requirement.md` + 验收标准表 | lead |
| arch → dev | `technical-design.md` + 任务拆分 + 风险表 | lead |
| dev → sdet | 代码 + **单测执行证据** | lead |
| sdet → qa | E2E 脚本 + **实际执行报告** | lead |
| qa → lead | 核对表 + 质量结论 | lead |

> **Lead 只做协调与验收，不写代码、不写文档正文、不跑测试。**
> 这条是角色分工的核心约束——一旦 Lead 亲自下场，独立验收就不存在了。

**与 Agent Teams 任务板的对应**：用 `blocked_by` 表达上表的串行依赖，
这样 `claim` 时上游会强制校验前置任务已完成（详见主 README §7）。

## 7. 派活模板

Lead 派活时按此格式（可直接填进 `spawn_teammate` 的 `prompt`）：

```
角色：<pm|arch|dev|sdet|qa>
任务：<一句话>
输入：<文件路径 / 上一步产物>
产物：<必须产出的文件与证据>
验收：<可判定的检查项>
红线：<本角色不得做的事>

背景：<为什么做，2~4 句——fresh context 的 teammate 需要它>
工作目录：<绝对路径>
禁止：<不要碰的目录/文件>
```

## 8. 反模式

| 反模式 | 为什么不行 |
|---|---|
| 先写全部测试再写全部实现 | 水平切片，测的是想象的行为 |
| mock 内部协作者 | 重构即挂，测的是实现 |
| "本地跑过了" | 环境不一致；必须有可复现证据 |
| "E2E 脚本写好了"但没跑 | 等于没做 |
| 用单测冒充 E2E | 层级不同，不可替代 |
| Lead 亲自写代码 | 破坏角色分工，失去独立验收 |
| 跳过覆盖分析直接写测试 | 假通过、边界遗漏 |
| 角色越多越好 | 名额有限且不可回收（主 README §2），协调成本随角色数上升 |

---

## 9. 怎么按需裁剪

不是每个项目都需要 5 个角色。**从最小可用集开始**：

| 场景 | 建议角色 | agent 数（含 lead） |
|---|---|---|
| 只做调研 | 2~4 个专项 researcher | 3~5 |
| 小功能 | pm + dev + qa | 4 |
| 标准功能 | pm + arch + dev + sdet + qa | 6 |
| 大型改造 | 同上 + 多个 dev 按模块切分 | 6~8 |

**注意 agent 名额上限**（默认 16 teammate，当前 profile 配 8），
且名额**不可回收**——规划时要留缓冲，详见主 README §2。
